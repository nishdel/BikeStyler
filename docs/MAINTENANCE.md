# Publication and documentation maintenance

The public GitHub checkout is canonical for future public development. The pre-publication development folder, saved browser designs and richer private backups remain local archival material. Port any later work from that archive by a reviewed diff; never copy the whole private folder over the public tree. Keep personal projects outside tracked files and use portable export/import to move a design into a different origin.

The initial public history contains only the sanitized release. Local cleanup receipts, deployment configuration and original photographs are not part of this repository. Inspect the exact staged file set and commit metadata before each publication. Use a public identity and GitHub-provided no-reply address at repository scope.

README and focused `docs/` Markdown are canonical public documentation. Update the affected page alongside behavioural changes; do not maintain a second independent manual in a wiki. OpenWiki pages, when present, route to these sources with source hashes and claims. Refresh them through its supported begin/plan/submit/finish lifecycle. Watchers may detect drift and stage reviewed Markdown; they should not launch model inference.

The owner's existing [OmniLAB documentation system](https://github.com/nishdel/OmniLAB-Local-Agent-Bridge-) can register this repository with an exact local root, reviewed document allowlist, source-access boundaries and revision provenance. These settings belong in private integration configuration. Existing memory controls, resource guards and other project registrations are independent of BikeStyler.

Staging documentation, completing a native wiki lifecycle and embedding documents into an Open WebUI knowledge base are different operations. A resource-deferred index is not a synchronized index. Check revision and last-success status before relying on retrieved excerpts. No generated Q&A or model-inference acceptance is implied by successful deterministic registration/search.

## Catalogue and mobile update workflow

Integrate the tested feature branch by a normal fast-forward or reviewed merge; the archival pre-publication app remains separate. Reimport from the original archive only when intentionally updating the snapshot.

No local-model contribution or token-savings claim follows from those attempts.
